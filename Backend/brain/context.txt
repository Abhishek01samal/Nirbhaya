# 1. APPLICATION PURPOSE

The application is a web-based personal safety platform.

A user can start a safety journey/session, share location, monitor a ride, optionally enable AI voice danger detection, configure guardians, trigger an SOS, and receive emergency assistance.

The system combines:

* Real-time location tracking
* Ride monitoring
* AI voice danger detection
* Manual SOS
* Automatic safety-event-based SOS
* Guardian notification
* Nearby responder escalation
* Emergency escalation
* Emergency calling
* Safe-place discovery
* Crime-area visualization
* Transport search for guardians
* AI assistant
* Dashboard
* Feedback

The application is designed particularly around women's safety scenarios, but the actual website should support users of any gender.

# 2. VERY IMPORTANT PLATFORM CONSTRAINT

This is a normal web application.

Do NOT assume Android/iOS native capabilities.

The system cannot reliably guarantee:

* Always-running GPS after the browser is completely closed
* Always-on microphone after browser suspension/closure
* Hardware power-button SOS
* Silent SMS from a browser
* Background emergency actions when the browser is completely terminated
* Guaranteed offline emergency delivery

Therefore:

* Location monitoring happens while the browser/session allows geolocation.
* Voice monitoring happens only after explicit user consent and while the monitoring session is active.
* Emergency actions must be network-aware.
* Never claim that browser APIs provide native mobile capabilities they do not actually provide.

# 7. SOS STATE MACHINE

This is the core feature owned by Person 1.

The general lifecycle is:

```text
TRIGGER
   ↓
VERIFYING
   ↓
 ┌──────────────────────────────┐
 │                              │
 │ User says "mistake"          │
 ↓                              ↓
CANCELLED                    User confirms
notify nobody                    │
                                ↓
                              ACTIVE
                                ↓
                            GUARDIAN
                                ↓
                       NEARBY RESPONDER
                                ↓
                      EMERGENCY ESCALATION
```

There is also a timeout path:

```text
VERIFYING
    ↓
No response before timeout
    ↓
ACTIVE
```

The important rule is:

> Silence/no response during verification defaults to SOS activation.

This prevents a user from being left unprotected simply because they could not respond.

# 9. SOS VERIFICATION BEHAVIOR

When an SOS trigger occurs, depending on the trigger type and configured application behavior:

```text
Create SOS
     ↓
VERIFYING
     ↓
Notify user
     ↓
Show confirmation UI
```

The user sees something conceptually similar to:

```text
"Are you safe?"

"This alert was triggered because unusual activity was detected."

[ I'm Safe / Cancel SOS ]
```

If the user explicitly cancels:

```text
SOS → CANCELLED
```

No guardian or responder should be notified.

If the user confirms:

```text
SOS → ACTIVE
```

If the timer expires:

```text
SOS → ACTIVE
```

Do not let an LLM decide this state transition.

The transition must be deterministic backend logic.

# 10. SOS ESCALATION

After:

```text
SOS = ACTIVE
```

the system starts the escalation process.

The intended hierarchy is:

```text
LEVEL 1
Guardian
      ↓
if no acknowledgement
      ↓
LEVEL 2
Nearby responder
      ↓
if no acknowledgement
      ↓
LEVEL 3
Emergency service
```

The exact notification mechanism may evolve.

The backend must track:

* Which level is active
* Who was notified
* When they were notified
* Whether they acknowledged
* When they acknowledged
* Whether escalation occurred
* Current SOS status

Do not hard-code a fragile implementation that makes future escalation levels impossible to add.

# 12. SOS ACKNOWLEDGEMENT

When a guardian receives an SOS notification, they can acknowledge it.

Example:

```text

"Emergency alert from User A"

[ACKNOWLEDGE]
```

When acknowledged:

```text
guardian escalation status
        ↓
ACKNOWLEDGED
```

The user should receive a real-time update through Socket.IO.

Example:

```text

```

The backend must validate that the person acknowledging is actually an authorized recipient for that SOS.

Never allow an arbitrary authenticated user to acknowledge someone else's SOS.

# 13. SOS RESOLUTION

An active SOS can eventually be resolved.

Possible resolution sources:

* User
* Guardian
* Authorized responder
* Emergency flow

When resolved:

```text
SOS → RESOLVED
```

Then:

* Stop further escalation
* Stop pending notifications
* Notify relevant participants
* Record `resolvedAt`

Do not delete the SOS.

SOS history is important for auditing and safety records.

# 21. VERIFICATION TIMEOUT

Every verifying SOS has:

```text
verification.expiresAt
```

Example:

```text
now = 12:00:00
timeout = 10 seconds

expiresAt = 12:00:10
```

If no response arrives:

```text
VERIFYING
 ↓
timeout
 ↓
ACTIVE
 ↓
escalation starts
```

The timeout must be server-controlled.

Do not rely exclusively on frontend JavaScript timers.

The frontend timer is only visual.

The backend is authoritative.

---

# 22. IMPORTANT CONCURRENCY REQUIREMENT

SOS verification can experience race conditions.

Example:

At exactly the same time:

```text
Request A = CANCEL
Request B = TIMEOUT
```

The system must not produce:

```text
CANCELLED
ACTIVE
```

simultaneously.

Only one valid state transition should win.

Use appropriate MongoDB atomic operations, transactions, or conditional updates.

For example, transitions should conceptually be:

```text
VERIFYING → ACTIVE
```

or:

```text
VERIFYING → CANCELLED
```

but never:

```text
CANCELLED → ACTIVE
```

or:

```text
ACTIVE → CANCELLED
```

unless an explicitly supported transition exists.

Design the state machine carefully.

# 23. ESCALATION ENGINE

After:

```text
SOS = ACTIVE
```

call something conceptually like:

```text
sosEscalationService.start(sosId)
```

It should:

1. Load SOS
2. Load active guardians
3. Sort guardians by priority
4. Notify appropriate guardian(s)
5. Record notification time
6. Wait for acknowledgement
7. If no acknowledgement within configured escalation window:

   * escalate
8. Notify nearby responders
9. If still unresolved:

   * emergency escalation
10. Stop immediately if SOS becomes resolved/cancelled where applicable

Do not scatter escalation logic across controllers.

Prefer:

```text
controller
    ↓
service
    ↓
state machine / escalation service
    ↓
notification layer
```

# 35. STATE TRANSITION RULES

Treat SOS as a finite-state machine.

Initial:

```text
VERIFYING
```

Valid transitions:

```text
VERIFYING → ACTIVE
VERIFYING → CANCELLED

ACTIVE → ESCALATING
ACTIVE → ACKNOWLEDGED
ACTIVE → RESOLVED

ESCALATING → ACKNOWLEDGED
ESCALATING → RESOLVED

ACKNOWLEDGED → RESOLVED
```

You may adjust exact transitions if implementation requires it, but:

> Never allow arbitrary status updates directly from the client.

For example, never accept:

```json
{
  "status": "RESOLVED"
}
```

from an ordinary user and blindly save it.

The backend must determine whether the transition is valid.

# 47. IDEMPOTENCY AND DUPLICATE SOS

This is an important safety requirement.

The same safety event may accidentally be delivered twice.

For example:

```text
OFF_ROUTE event
OFF_ROUTE event
```

within milliseconds.

The backend should avoid creating multiple identical SOS events unnecessarily.

Consider using an event identifier:

```json
{
  "eventId": "...",
  "type": "OFF_ROUTE"
}
```

or an equivalent deduplication strategy.

For automatic triggers, design the service so repeated identical events do not create an SOS storm.

Example:

```text
OFF_ROUTE
OFF_ROUTE
OFF_ROUTE
OFF_ROUTE
```

should not create four active SOS events for the same incident.

---

# 48. IMPORTANT: DO NOT OVER-TRIGGER

A single user may generate multiple safety events while an SOS is already active.

Example:

```text
OFF_ROUTE
LONG_STOP
VOICE_DANGER
```

If there is already an active SOS for the same safety session, do not blindly create three separate SOS events.

Instead:

```text
existing active SOS
       ↓
record/add new trigger information if appropriate
```

or ignore duplicate triggers according to the defined policy.

Keep one primary active emergency state per relevant safety session unless the product explicitly requires otherwise.
